# 2. Project background

The project is a web-based digital twin for an airborne communication node serving ground terminals over an X-Band air-to-ground network.

The original implementation was Python-based. The project was subsequently migrated to TypeScript with a browser Web Worker handling the active simulation.

**Important architectural clarification: Python is legacy code. TypeScript and the Web Worker are the active implementation.**

Do not spend time maintaining Python/TypeScript parity or repairing the legacy Python backend unless explicitly requested.

## Project objective

Build an interactive simulation environment in which users can:

- Visualize an airborne communication node and multiple ground terminals.
- Observe terrain-dependent radio-link behavior.
- Model traffic queues and QoS classes.
- Compare scheduling algorithms.
- Observe dynamic time-slot allocation.
- Inspect node status, link quality, queue backlog, and scheduler metrics.
- Modify the spatial scenario and observe the resulting changes in the simulation.
- Review historical simulation frames.

The simulation uses a 20 ms superframe configuration, an X-Band carrier configuration of 8 GHz, terrain-aware propagation, and dynamic scheduling.

The existing simulation has a legacy static scheduler and a dynamic scheduler called Tac-TAD in the project code. Tac-TAD is a project-defined algorithm, not an established standards designation.

# 6. Feature specification: communication visualization

## Required behavior

Display a persistent communication link between the ACN and each ground node.

The interface must distinguish:

- Available links.
- Degraded links.
- Obstructed or unavailable links.
- Links with scheduled or reported traffic.
- Links that are available but not currently carrying payload.

Provide two visual layers.

### Link layer

Render lines connecting the ACN to ground nodes. Use consistent visual styles for the link states, with a legend.

Selecting a node or link should highlight it and expose available metrics.

### Traffic layer

Render animated pulses or packet-like markers along links when actual simulation telemetry indicates that traffic is being served.

Traffic animation must not invent packet counts, throughput, or transmission events.

Provide a toggle to hide or show the traffic layer.

### Metrics

Where available, expose:

- Link status.
- SNR.
- Modeled bitrate.
- Queue backlog.
- Scheduled airtime.
- Payload service or goodput.
- Relevant scheduler allocation information.

All values must come from the active TypeScript simulation.

### Directionality caveat

The current scheduler is primarily an uplink scheduling model.

Showing bidirectional communication links does not mean that the simulation contains a complete downlink scheduler.

The interface must distinguish:

- A physically/modelled link that could support communication.
- Actual uplink scheduling and traffic.
- Downlink capability or telemetry, if present.
- Downlink data that is not currently modeled.

Do not fabricate downlink throughput merely to make the visualization look bidirectional.

# 7. Feature specification: frame history

Implement a bounded history buffer of immutable simulation snapshots.

## Requirements

- Default retention target: 60 seconds.
- Nominal frame rate: 50 frames/s.
- Nominal capacity: 3,000 snapshots.
- Support a timeline scrubber.
- Allow selecting a past frame.
- Allow returning to live mode.
- Keep simulation execution independent of historical inspection.
- Show the selected frame's time and frame index.
- Handle missing or expired frames explicitly.
- Keep snapshot memory bounded.

Do not store the full terrain raster in every frame. Terrain is mostly static and should be referenced separately.

## Snapshot contents

Store the information required to reconstruct the visual and diagnostic state:

- Frame index.
- Simulation time.
- Scenario/configuration revision.
- ACN position and trajectory state.
- Ground-node positions and relevant state.
- Link states and available communication metrics.
- Scheduler allocations.
- Queue and drop counters.
- Obstacle geometry or a reference to an immutable configuration revision.
- Any additional information required to render the frame faithfully.

If historical snapshots reference configuration revisions, those revisions must remain available for as long as dependent snapshots are retained.

## Live versus historical behavior

The worker continues running while the user inspects history unless the user explicitly pauses the simulation.

The frontend renders the selected snapshot without mutating the live simulation.

New frames continue entering the history buffer.

Returning to live mode selects the newest available frame.

A historical frame must not silently become a live frame when it expires.

Spatial edits must be recorded as configuration changes so that a frame from before an edit still represents the old configuration.

The 60-second retention target must be verified with memory profiling before being considered guaranteed.

# 8. Feature specification: editable flight paths

Support two explicit trajectory modes.

## Ellipse mode

Preserve the existing elliptical trajectory model.

Allow editing:

- Center.
- Semi-major axis.
- Semi-minor axis.
- Rotation.
- Speed, if supported by the existing configuration.
- Altitude, as a separate parameter.

Preserve the existing arc-length-based movement behavior and predictive occlusion integration.

Do not replace a working trajectory model unnecessarily.

## Waypoint mode

Allow users to:

- Add waypoints.
- Move waypoints.
- Remove waypoints, subject to minimum path requirements.
- Edit supported speed or altitude parameters.
- Switch explicitly between ellipse and waypoint modes.

The selected waypoint path is closed and repeats indefinitely.

The implementation must define:

- Interpolation method.
- Speed behavior.
- Loop-boundary continuity.
- Minimum valid waypoint count.
- Duplicate-point handling.
- Behavior for degenerate paths.
- Predictive look-ahead on the waypoint trajectory.

A suitable initial design is a closed polyline or a smooth closed curve with deterministic arc-length parameterization. Select the least invasive option that fits the existing trajectory engine.

The trajectory engine should expose a common interface conceptually equivalent to:

- `getAcnPosition(t)`
- `getAcnVelocity(t)`

The exact signatures should follow the existing implementation.

Predictive occlusion must use the selected trajectory implementation, not assume that all trajectories are ellipses.

When a trajectory edit is invalid, retain the previous valid trajectory.

Use one authoritative lock state rather than separate independent locks for each feature.

The initial default lock state should be chosen after inspecting the existing application. Do not silently alter established user workflows without justification.

# 11. Feature specification: path profile, obstacles, and top view

This feature consists of three connected capabilities.

## 11.1 Zoomable path profile

Extend the existing profile.

Required controls:

- Horizontal zoom.
- Vertical zoom.
- Pan.
- Reset-to-fit.
- Coordinate/distance readouts.
- Selected-link indication.

Display:

- Terrain elevation along the selected communication path.
- ACN and ground-terminal altitudes.
- Line of sight.
- Fresnel clearance where supported by the existing model.
- Custom obstacle intersections.
- Relevant obstruction information.

The horizontal axis represents distance along the selected path; the vertical axis represents elevation using a consistent vertical reference.

Zooming must only change the view transform, not the terrain data or simulation state.

Changing the selected node, ACN trajectory, or obstacle configuration must refresh the relevant profile.

## 11.2 Custom obstacle editor

Initial shapes:

- Cuboid.
- Cone.
- Pyramid.

Each obstacle should have:

- Stable ID.
- Shape.
- Horizontal position.
- Footprint dimensions.
- Height.
- Orientation where applicable.
- Vertical reference/ground anchor.

### Ground-anchored behavior

The obstacle is anchored to the terrain at its defined anchor point.

Conceptually:

`baseElevation = terrainElevation(anchorX, anchorY)`

`topElevation = baseElevation + obstacleHeight`

The exact geometry differs by primitive.

The original DEM must not be overwritten.

Store obstacles as separate geometry objects and render them over the terrain.

### Radio propagation integration

The obstacles must affect actual modeled obstruction.

A purely decorative obstacle is not sufficient.

The obstruction evaluator must account for:

1. Underlying terrain.
2. Custom obstacle geometry.
3. The ACN-to-ground-terminal line segment.
4. Relevant Earth-curvature and Fresnel-clearance calculations already supported by the model.

Start with deterministic geometric intersection tests for cuboids, cones, and pyramids.

The implementation must define how terrain and obstacle obstruction results are combined without double-counting the same physical obstruction.

Moving or resizing an obstacle must invalidate affected geometry and link-state caches.

Allow overlapping obstacles if the implementation can evaluate them deterministically and retain their identities.

Reject invalid dimensions and unsupported placements.

## 11.3 Top-view mode

Provide a toggle between the existing map view and a top-down spatial view.

The top-down view must display aligned:

- Terrain.
- ACN.
- Ground nodes.
- Flight path.
- Obstacle footprints.
- Communication links.

The same world-to-screen and screen-to-world transforms should be reused where practical.

Switching view modes must not mutate simulation coordinates.

The initial renderer remains Canvas. A true perspective 3D renderer is outside the current baseline scope.

# 12. Feature specification: ground-node AGL offset

Each ground node receives a configurable AGL offset in meters.

Conceptually:

`absoluteAltitude = terrainElevation(x, y) + aglOffset`

For example, if local terrain elevation is 3,200 m and AGL is 2 m, the modeled absolute altitude is 3,202 m, assuming both use the same vertical reference.

## Required behavior

- AGL is editable in the node inspector or inventory.
- Moving a node horizontally resamples the terrain.
- The configured AGL offset remains constant when the node moves.
- Absolute altitude updates with terrain elevation.
- The same derived position is used by propagation, obstruction, and rendering.
- Invalid AGL values are rejected.
- Out-of-coverage behavior follows a documented policy.
- The ACN altitude is configured separately from ground-node AGL.

Centralize ground-node position construction. Do not independently add antenna heights in the map renderer, terrain model, or link-budget code.

Replace the previous hidden/fixed ground-node antenna-height assumption with an explicit per-node configuration.

# 14. Web Worker protocol

The worker owns the active simulation and validates every mutation.

The existing protocol should be extended carefully, preserving current commands unless a deliberate migration is necessary.

## Proposed commands

New commands may include:

- `SET_SPATIAL_LOCK`
- `SET_TRAJECTORY`
- `MOVE_NODE`
- `SET_NODE_AGL`
- `UPSERT_OBSTACLE`
- `DELETE_OBSTACLE`
- `SET_OBSTACLE_TRANSFORM`
- `REQUEST_SCENARIO_STATE`
- `REQUEST_FRAME_SNAPSHOT`

Mutating commands should include:

- A request ID.
- The relevant object ID.
- The desired new values.
- An expected scenario revision.

For example:

```typescript
{
  type: "MOVE_NODE",
  nodeId: 12,
  position: { xM: 1000, yM: 2000 },
  expectedRevision: 7,
  requestId: "move-123"
}
```

This is an illustrative payload, not necessarily the final shape.

## Revision checks

If a command uses an outdated revision, reject it rather than applying it to stale state.

Every accepted spatial mutation increments the revision.

Invalid commands must not partially mutate the state.

## Proposed responses

- `COMMAND_ACCEPTED`
- `COMMAND_REJECTED`
- `SCENARIO_STATE`
- `FRAME_SNAPSHOT`
- `SIMULATION_FRAME`
- `HISTORY_STATUS`

Rejections should carry a reason such as:

- `LOCKED`
- `INVALID_INPUT`
- `STALE_REVISION`
- `NOT_FOUND`
- `OUT_OF_BOUNDS`

The exact union should follow the existing error-handling architecture.

The current worker's telemetry should be adapted into the new normalized frame representation at the worker boundary. Do not rewrite the scheduler or link-budget engine simply to rename messages.

## Worker lifecycle

For an accepted spatial mutation:

1. Validate the lock.
2. Validate the revision.
3. Validate the input.
4. Validate bounds and geometry.
5. Construct the candidate configuration.
6. Rebuild dependent trajectory or spatial state.
7. Invalidate relevant cached calculations.
8. Atomically commit the new configuration.
9. Increment the scenario revision.
10. Acknowledge the command and publish the accepted state.
11. Ensure subsequent simulation frames use the new revision.

For rejected commands, preserve the previous valid state.

The frontend may display a local drag preview but must restore authoritative state if the worker rejects the final edit.

# 19. Existing risks and deferred work

A prior source-level review identified several issues that should be tracked but are not the immediate implementation priority.

## Terrain coordinate scaling

The DEM downloader covers a much smaller geographic region than the default 1,200 km simulation grid. The terrain can therefore be stretched across an inappropriate spatial extent.

The raster artifacts were internally consistent, but file consistency does not establish correct geographic mapping.

Defer the comprehensive terrain-coordinate correction unless a feature cannot be implemented correctly without it. Do not conceal the mismatch when implementing obstacle or path geometry.

## Physical-model validation

The terrain, diffraction, Fresnel, RF link-budget, and predictive occlusion models require additional independent validation.

Do not claim standards compliance merely because the code references ITU-R or 3GPP documents.

## Benchmark validity

Historical benchmark results need rerunning after metric corrections.

Reported metrics have previously included issues with latency percentiles, wall-clock versus simulated-time interpretation, and insufficient reproducibility.

Do not use historical benchmark results as proof that the new features or current scheduler are scientifically validated.
