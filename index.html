1. Project overview

The X-Band Digital Twin simulates an aerial communication node (ACN) serving sixteen registered ground nodes over a terrain-aware air-to-ground network. Ground nodes represent dismounted tactical terminals and a command-post class. Traffic is generated into QoS queues, links are evaluated from geometry and RF assumptions, and a TDMA scheduler allocates the shared uplink.

The platform is intended for controlled research demonstrations of terrain-induced outages, queue behavior, link adaptation, and adaptive airtime allocation. It demonstrates a browser-hosted simulation with telemetry, map views, scheduler diagnostics, path editing, and historical inspection. It does not ingest measured aircraft telemetry, synchronize with a live network, or establish operational performance.

Research comparison: Legacy_Static_TDMA assigns fixed equal uplink slots, while Tac-TAD adapts allocation using queue urgency, link state, and predictive terrain transitions. A fair comparison requires identical configuration, traffic, terrain, duration, and metric definitions.

The worker is the authority for simulated physics and scheduling. UI code sends explicit commands such as pause, resume, step, reset, and configuration updates; it consumes worker messages for rendering. Canvas drawing and historical inspection do not create an alternate physics state.

The physical simulation frame is 0.020 s (50 Hz). Playback speed changes the timer cadence used to request frames; it does not change the physical timestep. A STEP command advances one physical frame.

3. Simulation engine

At each 20 ms frame the worker advances simulation time, evaluates the ACN trajectory, updates ground-node and predictive terrain state, evaluates terrain and obstacle geometry, computes link status and bitrate, generates or services traffic, runs the selected scheduler, and publishes telemetry. The exact internal ordering is an implementation detail of SimulationWorkerManager; consumers must treat the published frame as the coherent observation boundary.

State familyCurrent behavior
ACNPosition, velocity, heading, altitude, coverage radius, and trajectory mode are published from the trajectory engine.
Ground nodesSixteen registered IDs are maintained in local Cartesian coordinates with configured ground/AGL state.
LinksSlant geometry, terrain clearance, obstacle state, losses, SNR, MODCOD, bitrate, and outage classification are evaluated per node.
NetworkTraffic queues evolve, packets are dequeued according to the schedule, and goodput/waste/drop counters are emitted.

4. UAV flight and trajectory model

Ellipse mode follows a rotated, arc-length-parameterized ellipse. Waypoint mode accepts a closed route (the last point connects to the first), validates the route, builds a cubic Hermite spline with shared bounded tangents, samples it at 512 samples per segment by default, and evaluates position by arc length. The route is therefore smooth and closed, but it is not a learned or aerodynamic flight controller.

  • Physical speed: the configured true-air-speed target in metres per second. The default is 60 m/s.
  • Speed transitions: positive acceleration and deceleration limits bound changes when speed or mode changes.
  • Stationary hold: a speed of 0 m/s freezes trajectory progress. This is a simulation hold and must not be interpreted as fixed-wing hovering.
  • Playback speed: a wall-clock frame-request multiplier (0.1×–10×; UI step 0.05×; presets 0.5×, 1×, 2×, 5×, 10×). It changes execution cadence only and does not alter the 20 ms physical timestep, the configured target airspeed, or link/scheduling results.
  • Telemetry: position and velocity provide heading through the velocity vector; altitude is configured as MSL.

5. Terrain and geographic model

The real-terrain metadata describes a 512 × 512 point-registered Ladakh raster centered at 34.5°N, 76.5°E, spanning 33.5–35.5°N and 75.5–77.5°E. The local projection is equirectangular at the center latitude. The documented pixel scales are approximately 359.45 m in X and 434.17 m in Y; these are the source grid scales, not sub-metre terrain accuracy.

6. RF propagation and link budget

The implemented link budget is a deterministic engineering approximation. Received power sums transmit power and antenna gains, then subtracts free-space path loss, terrain diffraction, gaseous loss, rain loss, cable loss, and implementation margin. Thermal noise uses kBTB × 10^(NF/10); SNR is received power minus noise in dB.

FSPL = 20 log₁₀(d) + 20 log₁₀(fc) + 20 log₁₀(4π/c)
Pnoise = kBT · B · 10^(NF/10)
SNR = Prx − Pnoise

At the default 8.0 GHz carrier and 1.0 MHz bandwidth, the model uses ITU-R-inspired simplified coefficients for clear-air gas attenuation and horizontal-polarization rain attenuation, with a 10 km rain-cell cap. A discrete eight-entry DVB-S2X / 3GPP Rel-17 NTN-inspired MODCOD table maps SNR to spectral efficiency; it is an abstraction, not a conformance implementation.

Obstacle intersections force outage classification but do not infer scattering or an additional electromagnetic attenuation term. Antenna patterns, multipath, interference, polarization mismatch, calibration error, and measured weather profiles are not represented.

7. TDMA scheduling algorithms

Each superframe contains a 1 ms control period, a dynamic 3–7 ms downlink window, and a nominal 16 ms uplink region. A 12 μs timing-advance guard and 200 μs minimum allocation constrain dynamic slots.

SchedulerDecision behavior
Static TDMADivides available uplink equally across registered nodes. It dequeues up to fixed-slot capacity even when a link is in outage, so payload may be counted as wasted on outage.
Tac-TADDeterministic heuristic scheduler. It scores urgency from QoS priority, backlog, head-of-line delay, current link quality, and predictive terrain state; it sizes allocations to eligible queued demand and reclaims severed-link airtime.
Pre-occlusion flushPredictive look-ahead can prioritize evacuation of queued payload before a predicted hard shadow. This is a rule-based surge, not machine learning.
OutputEach allocation reports node, start, duration, timing advance, MODCOD, spectral efficiency, capacity, and whether it is a pre-occlusion flush.

Tac-TAD is not a reinforcement-learning policy, neural network, trained model, or learned checkpoint. No training procedure or learned weights exist in the current implementation.

8. Queue, packet, and metric model

Each node uses bounded strict-priority queues for 5QI 69 Emergency C2, 65 MC PTT voice, 67 MC video, and 70 tactical photo. The default queue capacity is 400 packets with a 120-packet ceiling for 5QI 69. Lower-priority traffic is evicted first when the buffer is full; non-C2 packets are pruned when their packet delay budget expires.

Queue drops are not RF failures. Overflow drops occur at admission, delay drops occur at expiry/pruning, and outage waste counts payload dequeued by a schedule but not deliverable because the link is unavailable. Goodput counts only payload dequeued while the link is usable. The UI also reports backlog, scheduled airtime, utilization, and per-frame/cumulative drop counters.

9. Visualization and data communication

The Overview keeps a live 2D map visible while workspace tabs expose scheduler, terrain/RF, terminal inventory, and documentation views. Main 2D Map, Terrain Top View, RF Top View, and 3D Terrain are presentation layers over worker telemetry; they do not calculate authoritative physics.

The communication view renders control/broadcast phases, uplink and downlink allocations, guard intervals, idle/reclaimed intervals, conflicts, and packet activity. A STEP request advances one physical frame, while the visual timeline may expand or annotate events for inspection. Live and historical data are kept separate so a scrubbed view does not overwrite the live simulation.

The flight-path editor validates closed waypoint routes before committing them to the worker. The obstacle editor supports cuboids, cones, and pyramids with spatial locking and bounded dimensions. Obstacles intersecting a path are treated as geometric blockers; this is not a complete scattering model.

10. History and replay semantics

The UI maintains rolling telemetry and scheduler history for inspection, including a 3,000-frame / approximately 60-second timeline where configured. Historical scrubbing selects stored snapshots; it does not rewind and deterministically re-execute the worker. Returning to LIVE resumes the current worker observation stream. Therefore, history should be described as telemetry snapshot inspection, not full deterministic replay.

12. Research methodology and experimental evaluation

The intended evaluation is a paired, controlled comparison of Legacy_Static_TDMA and Tac-TAD. The two scheduler arms must receive the same initial terrain, ACN route and motion, node positions, traffic configuration, RF/environment parameters, simulation duration, and random inputs where randomness is introduced. Only the scheduler policy should differ. A single browser session is useful for exploration, but comparative claims should be generated from recorded run manifests and repeatable worker runs.

12.1 Experimental procedure

  1. Record the commit, runtime, host, scheduler policy, scenario, terrain asset/version, RF and weather parameters, trajectory, node inventory, traffic profile, duration, and seed or seed status.
  2. Warm up both arms using the same initialization rule, then run each for the same number of 20 ms frames. Keep the physical frame count separate from wall-clock execution time.
  3. Use paired scenarios: for each scenario identifier, run Static TDMA and Tac-TAD with identical inputs. Randomized scenario order may be used to reduce ordering effects, but the pairing must be retained.
  4. Export raw observations before aggregation. Keep failed, incomplete, and excluded runs with an explicit reason rather than silently removing them.
  5. Report results by scenario and in aggregate, with sample count, missing data, uncertainty, and the exact denominator for every percentage.

12.3 Statistical evaluation plan

For each paired scenario, calculate the Tac-TAD minus Static difference (and the ratio only when the denominator is meaningful). Summarize paired differences with mean, median, standard deviation, interquartile range, and confidence intervals. Use a paired t-test only when the distribution and independence assumptions are defensible; otherwise use a paired Wilcoxon signed-rank test or a permutation/bootstrap interval over scenario-level paired differences. Report effect sizes alongside p-values, correct for multiple primary comparisons when several hypotheses are tested, and treat confidence intervals crossing zero as inconclusive rather than as evidence of equivalence.

Frames within one run are temporally correlated, so they must not be treated as independent experimental replicates. The recommended unit of inference is the paired scenario/run, with seeds or independently constructed scenarios as replicates. Pre-register primary metrics, exclusion rules, minimum run counts, and stopping criteria before inspecting comparative outcomes.

Interpretation rule: an observed Tac-TAD improvement is a result for the specified model and scenario distribution. It is not evidence of universal scheduler superiority, field performance, or real-time operational suitability.

Appendix A. Mathematical background and technical formulation

This appendix records the mathematical formulations used by the active TypeScript/WebWorker implementation. It is an engineering traceability document, not a claim that the project implements every referenced standard in full. Equations marked established are common engineering identities; equations marked standard-based approximation follow the project’s documented interpretation of a reference; equations marked project-defined or heuristic describe local implementation behavior.

Notation and units. Distances are in metres, time in seconds, frequency in hertz, speed in metres per second, power in dBm or watts as stated, and angles in radians unless degrees are explicitly shown. Every equation below has a unique appendix identifier and a source/function mapping.

A.1 Radio propagation and link geometry

(A-1)   d₂D = √(Δx² + Δy²),    d₃D = √(Δx² + Δy² + Δz²)
         Δx = xA − xN,   Δy = yA − yN,   Δz = zA − zN

Variables: (xA,yA,zA) is the ACN position in m MSL/local Cartesian coordinates; (xN,yN,zN) is the node position; Δx,Δy,Δz are component differences; d2D is horizontal range and d3D is slant range, all in m. Interpretation: this is the separation used by propagation delay and FSPL. Source: established Euclidean geometry; TerrainEngine.computeSlantGeometry in src/core/terrain.ts. Limits: local Cartesian coordinates and endpoint heights are assumed; geodetic transformation and terrain datum errors are outside this equation.

(A-2)   τprop = d₃D / c,    τTA = 2τprop = 2d₃D / c

Variables: τprop is one-way propagation delay in s; τTA,geom is the geometry-derived two-way timing value in s; c is the configured speed of light in m/s. Interpretation: the terrain geometry telemetry computes a two-way propagation relation. Scheduler allocation records currently use a separate fixed timingAdvanceS = 0.001 s field and do not consume τTA,geom. Source: established propagation identity; computeSlantGeometry, plus fixed allocation field in both scheduler implementations. Limits: neither value is a complete MAC timing-advance procedure; clock, synchronization, and waveform processing delay are not modeled.

(A-3)   φ = d₂D / R′e,    e = atan2((R′e + zA)cosφ − (R′e + zN), (R′e + zA)sinφ)

Variables: R'e = kRe is effective Earth radius in m; φ is central angle in rad; e is elevation angle, converted to degrees for telemetry. Interpretation: the implementation uses an effective-radius Earth geometry. Source: standard-based approximation associated with ITU-R P.834; computeSlantGeometry and EnvironmentConfig.effectiveEarthRadiusM. Limits: k = 4/3 is fixed by default; no measured refractivity profile is used.

A.2 Terrain obstruction, LOS/NLOS and Fresnel-zone analysis

(A-4)   s = d₁ / D,   (x(s),y(s),zLOS(s)) = (xN,yN,zN) + s(Δx,Δy,Δz)

Variables: D = d3D; d1 is distance from node to a sampled path point; d2 = D − d1; s is the path fraction; zLOS is linearly interpolated endpoint height. Interpretation: the terrain engine samples this ray at a configured interval, normally 100 m. Source: project-defined path sampling in TerrainEngine.evaluateTerrainObstruction. Limits: finite sampling can miss sub-interval terrain features; out-of-coverage paths return invalid clearance rather than fabricated terrain.

(A-5)   hclear(d₁) = zLOS(d₁) − [hDEM(d₁) + bEarth(d₁,d₂)]
         bEarth(d₁,d₂) = d₁d₂ / (2R′e)

Variables: hDEM is sampled terrain elevation in m; bEarth is effective-Earth bulge in m; hclear is clearance in m. Interpretation: positive clearance is above the effective terrain/curvature surface. Source: project implementation in TerrainEngine.computeEarthBulge and evaluateTerrainObstruction, with effective-radius basis from ITU-R P.834. Limits: the parabolic bulge is an approximation and is not a full spherical ray-trace or refractivity solution.

(A-6)   r₁(d₁,d₂) = √(λd₁d₂ / D),    ρ = hclear / r₁

Variables: r1 is first Fresnel-zone radius in m; λ = c/fc is wavelength in m; ρ is normalized clearance. Interpretation: the engine retains the path sample with minimum normalized Fresnel clearance. Source: established Fresnel-zone relation; evaluateTerrainObstruction. Limits: only the first-zone scalar clearance is used; antenna patterns, phase, multipath, and partial-zone field integration are not modeled.

(A-7)   LOS = (ρ ≥ 0.6) ∨ (0 < ρ < 0.6) with diffraction penalty; NLOS/outage geometry when ρ ≤ 0

Variables: ρ is the minimum ratio in (A-6). Interpretation: the implementation preserves an isLos boolean for positive clearance, but assigns a nonzero diffraction loss when clearance is below 0.6 Fresnel radius; nonpositive clearance is treated as terrain obstruction. Source: project-defined threshold behavior in evaluateTerrainObstruction and linkStatusClassifier.ts. Limits: the threshold is not presented as a universal LOS standard.

A.3 Knife-edge diffraction

(A-8)   ν = −hclear √[(2/λ)(1/d₁ + 1/d₂)]

Variables: ν is the dimensionless knife-edge parameter; for the obstructed branch hclear ≤ 0, so the implemented sign convention yields a nonnegative obstruction parameter. Source: established knife-edge diffraction form, implemented in evaluateTerrainObstruction. Limits: sign conventions and the sampled dominant obstacle must not be generalized beyond this implementation.

(A-9)   LKE = 6.9 + 20log₁₀(√[(ν − 0.1)² + 1] + ν − 0.1)
         Ldiff = LKE + 12 dB

Variables: LKE and Ldiff are losses in dB; the fixed 12 dB term is the project’s rounded-crest/Fock penalty. Source: knife-edge expression associated with ITU-R P.526; the added 12 dB term is project-defined in evaluateTerrainObstruction. Limits: the project does not claim a complete P.526 implementation, multiple-edge diffraction, scattering, or validated rounded-crest calibration. The exact publication edition/equation mapping should be verified before formal citation.

A.4 Atmospheric attenuation and RF link budget

(A-10)   FSPL = 20log₁₀(d₃D) + 20log₁₀(fc) + 20log₁₀(4π/c)

Variables: FSPL is free-space path loss in dB; d3D is m; fc is Hz; c is m/s. Source: established Friis/free-space path-loss identity; LinkBudgetEngine.computeFsplDb. Limits: isotropic/free-space assumptions do not include terrain, multipath, antenna pattern, or interference; terrain diffraction is added separately.

(A-11)   Lgas = 0.012(d₃D / 1000) dB
         γR = kHRαH,   Lrain = γR min(d₃D/1000, ℓrain)

Variables: Lgas and Lrain are dB; R is rain rate in mm/h; kH = 0.00411, αH = 1.39; ℓrain is rain-cell length in km. Source: simplified ITU-R P.676/P.838-3-inspired terms in computeGaseousAttenuationDb and computeRainAttenuationDb. Limits: the coefficient is fixed for the configured 8 GHz/horizontal-polarization assumption; no full frequency-, elevation-, or weather-profile integration is performed.

(A-12)   Ltotal = LFSPL + Ldiff + Lgas + Lrain + Lcable + Mimpl
         Prx = Ptx + Gtx + Grx − Ltotal

Variables: losses and margin are dB; Ptx/Prx are dBm; Gtx/Grx are dBi; Lcable and Mimpl are configured dB terms. Source: project link-budget summation in LinkBudgetEngine.evaluateLink. Limits: the receiver gain is represented by the ACN gain field and the model does not resolve directional patterns or link asymmetry beyond configured node transmitter parameters.

A.5 Receiver noise, SNR and link adaptation

(A-13)   Pnoise,W = kBT B 10NF/10,    Pnoise,dBm = 10log₁₀(1000Pnoise,W)
         SNRdB = Prx,dBm − Pnoise,dBm

Variables: kB is Boltzmann’s constant in J/K; T is temperature in K; B is bandwidth in Hz; NF is noise figure in dB; powers are W/dBm. Source: established thermal-noise relation and dBm conversion; computeThermalNoiseFloorDbm and evaluateLink. Limits: constant temperature and scalar noise figure are assumed; interference and implementation-specific receiver effects are represented only by configured margin.

(A-14)   η(SNR) = ηj for the highest threshold γj ≤ SNR;    RPHY = η(SNR)B

Variables: γj is a MODCOD minimum-SNR threshold in dB; ηj is spectral efficiency in bit/s/Hz; η is selected efficiency; RPHY is nominal bitrate in bit/s. Source: threshold lookup and bitrate calculation in selectModCod and evaluateLink. Limits: this is link adaptation by table lookup, not a waveform, coding, HARQ, or modem simulation.

A.6 MODCOD and PHY capacity

The current table contains eight named tiers from pi/2-BPSK 1/3 at −1.5 dB and 0.33 bit/s/Hz through 64-APSK 5/6 at 22 dB and 4.95 bit/s/Hz. If no threshold is met, the table returns LINK_OUTAGE, zero spectral efficiency, and zero bitrate. These names are DVB-S2X / 3GPP Rel-17 NTN-inspired labels, not a claim of standards-compliant PHY behavior.

(A-15)   Cslot = ⌊τslotRPHY⌋ bits,    Bslot = ⌊Cslot/8⌋ bytes

Variables: τslot is scheduled payload duration in s; Cslot is integer slot capacity in bits; Bslot is dequeuing capacity in bytes. Source: LegacyStaticScheduler.scheduleFrame and TacTadScheduler.scheduleFrame. Limits: PHY capacity is an upper bound for the slot; actual delivered application goodput depends on queued bytes, packet fit, outage state, and scheduler service.

A.7 TDMA framing and resource allocation

(A-16)   TUL,avail = Tframe − Tctrl − TDL
         Tframe=0.020 s, Tctrl=0.001 s, TDL∈{0.003,0.005} s

Variables: all terms are seconds; TUL,avail is available uplink time. Source: constants and scheduler arithmetic in src/core/scheduler.ts. Interpretation: the current rule selects 3 ms normally or 5 ms when downlink backlog exceeds 5,000 bytes; a 7 ms maximum constant exists but is not reached by the current rule. Limits: this is not a complete bidirectional MAC protocol.

(A-17)   τstatic = [TUL,nominal − Nτguard] / N

Variables: N is registered node count; τguard = 12 μs; TUL,nominal = 16 ms; τstatic is equal payload slot duration. Source: LegacyStaticScheduler.scheduleFrame. Limits: static service dequeues packets even when the link is unusable, which is intentionally measured as outage waste in this model.

(A-18)   Tused = Σi∈alloc(τi + τguard),    UUL = 100 Tused/TUL,avail

Variables: τi is allocation duration; Tused is scheduled airtime including guards; UUL is utilization in percent. Source: both scheduler reports. Limits: utilization is airtime accounting, not application throughput or energy efficiency.

A.8 Traffic generation and queueing theory

(A-19)   λv = μvideo,frame,    K ~ Poisson(λv)

Variables: λv is configured mean video packets per frame; K is generated video packet count. Source: GroundNodeTrafficSubsystem.poissonDraw and generateTraffic. Limits: C2, voice, and photo generation follow deterministic interval/window/remaining-bytes rules; the Poisson process is per frame and is not a calibrated field traffic model.

(A-20)   Wp(t) = max(0,t − tarrival,p),    tdeadline,p = tarrival,p + PDBq

Variables: Wp is packet sojourn time in s; tarrival and tdeadline are packet timestamps; PDBq is the QoS profile delay budget. Source: Packet, enqueuePacket, getHolDelayS, and queue pruning in src/core/queues.ts. Limits: deadline pruning excludes 5QI 69 during the modeled shadow behavior; this is a project policy, not a universal QoS rule.

(A-21)   Qbits(t+) = Qbits(t) + Abits(t) − Dbits(t) − Xoverflow,bits(t) − Xexpiry,bits(t)

Variables: all terms are bits; Qbits is queued backlog; Abits is admitted packet payload; Dbits is dequeued service; Xoverflow,bits and Xexpiry,bits are the sizes of evicted or expired packets. Separately, runtime counters droppedOverflowCount and droppedDelayCount count packets, not bits. Source: project-defined conservation summary of FQCoDelQueue.enqueue, dequeue, and pruneExpiredPackets. Limits: the compact equation hides per-class ordering, packet-size fit, buffer ceilings, and eviction priority.

A.9 Tac-TAD and Static TDMA mathematical formulation

(A-22)   Ψi = Φevac,i · Ui · (Ri/max(1000,R̄i)) · max[1, log₂(1 + Qi/8000)]
         Ui = Σq∈active wq exp(min(8, HOLi,q/PDBq))

Variables: Ψi is Tac-TAD’s project-defined ranking score; Φevac is predictive evacuation/re-emergence boost; Ui is QoS urgency; wq is configured class weight; HOL is head-of-line age; PDB is delay budget; Ri is instantaneous bitrate; R̄i is the moving average; Qi is backlog bits. Source: exact structure in TacTadScheduler.scheduleFrame. Limits: this is a deterministic heuristic composite, not a Lyapunov proof, trained policy, or optimization solution.

(A-23)   τreq,i = Qi/Ri,    τi = min(τreq,i, τmax,normal, Tremaining − τguard)

Variables: τreq is requested service duration; τi is normal Tac-TAD allocation; τmax,normal is the scheduler’s configured normal cap; Tremaining is remaining uplink time. Source: exact-fit sizing in TacTadScheduler.scheduleFrame. Limits: a pre-occlusion flush changes the cap rule and can request at least the minimum slot; no global optimality or fairness guarantee follows.

(A-24)   Φevac = 1 + 5[(3 − tocc)/3]0..1 min(1,Qi/20000),   PRE_OCCLUSION_FLUSH
         Φevac = 4,   RE_EMERGENCE_BURST

Variables: tocc is predicted time to occlusion in s; [·]0..1 denotes the implementation’s nonnegative/clamped ratio; backlog is in bits. Source: project heuristic in TacTadScheduler.scheduleFrame. Limits: the warning horizon, factor 5, backlog scale, and re-emergence factor 4 are tuned constants; they require experimental sensitivity analysis.

A.10 Simulation timestep, state evolution and telemetry

(A-25)   tn+1 = tn + Δt,    fn+1 = fn + 1,    Δt = 0.020 s = 1/50 s

Variables: tn is simulated time; fn is frame index; Δt is the fixed physical timestep. Source: SimulationWorkerManager.tickSimulation and FRAME_DT. Interpretation: each tick refreshes obstruction state, generates/prunes traffic, runs both schedulers, accumulates metrics, and emits a telemetry frame. Limits: wall-clock timer interval and playback speed affect execution cadence only; they do not change Δt.

(A-26)   yn = {tn, fn, pACN, vACN, Li, Qi, Si, Mn}

Variables: yn is the published telemetry observation; pACN/vACN are position/velocity; Li is link state; Qi is queue state; Si is schedule/report state; Mn is accumulated metrics. Source: buildTelemetryFrame. Limits: telemetry is a snapshot at a worker frame boundary; it is not an event-sourced log of every internal operation.

A.11 Performance metrics and statistical evaluation

(A-27)   G = Σ bitsdelivered / Teval,    Woutage = Σ bitsdequeued,outage
         Bfinal = bitsbacklog at final frame,    Ddrop = Ddelay + Doverflow

Variables: G is delivered goodput in bit/s; Teval is the stated evaluation interval; Woutage is outage-wasted payload bits; Bfinal is the final-frame backlog; Ddrop separates delay and overflow packet counts. Source: worker metric accumulation and FrameScheduleReport; staticFinalBacklogBits and tacFinalBacklogBits are overwritten each frame rather than accumulated. Limits: denominators and window boundaries must be reported; PHY capacity, scheduled service, dequeued payload, and delivered goodput are different quantities.

(A-28)   Δj = mTac,j − mStatic,j,    CIα(Δ̄) = Δ̄ ± t1−α/2,n−1sΔ/√n

Variables: Δj is a paired scenario difference; m is a metric; n is the number of independent paired scenario/run replicates; sΔ is the sample standard deviation; CIα is a confidence interval when the paired-t assumptions are reasonable. Source: project evaluation formulation described in the methodology section, not runtime code. Limits: use paired Wilcoxon or bootstrap/permutation alternatives when assumptions fail; do not treat correlated frames as independent replicates.

15. Limitations and future research

Implemented capabilities

  • Browser TypeScript worker simulation at a 20 ms physical step.
  • Terrain-aware LOS/Fresnel/diffraction screening, configurable rain and gas terms, adaptive MODCOD abstraction, QoS queues, two TDMA policies, trajectory editing, obstacle geometry, map views, and telemetry history.

Simplifications and unresolved validation

  • No measured field telemetry synchronization or calibrated end-to-end channel model is present.
  • Terrain diffraction uses bounded geometric approximations; multipath, scattering, antenna patterns, interference, and polarization effects are not simulated.
  • The MODCOD table is a discrete engineering abstraction and is not proof of DVB-S2X or 3GPP conformance.
  • History stores telemetry snapshots and does not provide deterministic re-execution from a complete event log.
  • Legacy Python artifacts and archived benchmark numbers are not current TypeScript results unless parity is independently demonstrated.
Historical benchmark results (legacy Python engine): archived values are not a verified statement about the current TypeScript engine and must not be presented as current-worker measurements without a controlled Python ↔ TypeScript parity study. Data-quality flag: archived distributions require review before use in claims.

Recommended research extensions

  1. Calibrate propagation and antenna assumptions against measured link data.
  2. Define cross-engine golden fixtures only where legacy parity is required.
  3. Run paired multi-seed experiments with manifests, confidence intervals, and metric definitions.
  4. Profile worker latency, UI frame time, memory, and long-duration stability on named hardware.
  5. Extend the channel model with interference, weather profiles, and richer terrain/multipath treatment.
